# ADR-001 · 定位收窄：只做「翻译 + 翻译墙」

- 日期：2026-09-09
- 状态：已采纳

---

## 背景

原设计（v2.1）设想三大块全部在浏览器扩展内完成：页面翻译、剪藏 → Obsidian 导入、发稿。

## 决策

**浏览器扩展只做两件事：实时页面翻译 + 特定网站翻译墙突破。** 剪藏 / AI 加工 / 插图 / 发稿全部移交 Obsidian 生态。

| 环节 | 归属 | 理由 |
|---|---|---|
| 实时页面翻译 | 浏览器扩展 | 浏览器原生场景，Obsidian 无法替代 |
| 翻译墙突破 | 浏览器扩展 | 需要浏览器环境（Cookie / UA / JS / DOM） |
| 剪藏 / 加工 / 插图 / 发稿 | Obsidian 生态 | 各司其职、生态成熟 |

## 选项对比

| 选项 | 描述 | 权衡 |
|---|---|---|
| **A 全在扩展**（原设计） | 一个扩展做完三块 | 开发/维护成本高，重复造轮子 |
| **B 收窄定位**（本决策） | 扩展只做翻译+翻译墙 | 放弃一键闭环的顺滑，换取成本大降、生态可替换性 |

## 论据

- 实测 Obsidian Web Clipper 剪藏外文长文毫无压力
- 翻译 / 加工 / 插图 / 发稿均有 Obsidian 生态插件 + Agent 完整替代
- 浏览器是临时性工具，不适合做深度内容加工

## 后果

- ✅ 开发量从 5 阶段缩减到 1 核心 + 1 墙 + 3 可选项
- ✅ 维护成本大幅降低
- ⚠️ 需依赖用户安装 Obsidian 生态工具
- ⚠️ 不做剪辑无缝体验（浏览器一键 → Obsidian 双语笔记）

## 保留可选项

- Obsidian 轻量桥接（发当前页双语）—— 仅用户明确需要时立项
- 翻译缓存导出 —— 段落剪藏复用，降为非核心
